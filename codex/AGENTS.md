# Global Instructions — Router

This file is your index, loaded every session. It holds (1) **Always-On Rules** that apply to every turn, and (2) a **Rule Index** telling you which detail doc to read before a given kind of task. Everything else lives in `~/.ai-instructions/` — read those docs on demand; never preload them.

## Navigation protocol
Each `~/.ai-instructions/` doc opens with YAML frontmatter listing its `sections`. To use a doc: read ONLY the frontmatter + section list, then `grep` the `##` heading you need and read just that slice (Read with offset/limit). Do NOT read whole docs.

## Multi-tool setup
This user runs Claude Code, Gemini CLI, and Codex. Each reads its own files; keep them in sync.

| Tool | Global instructions | Global settings | Hooks |
|------|--------------------|-----------------|-------|
| Claude Code | `~/.claude/CLAUDE.md` | `~/.claude/settings.json` | yes |
| Gemini CLI | `~/.gemini/GEMINI.md` | `~/.gemini/settings.json` | yes |
| Codex | `~/.codex/AGENTS.md` | `~/.codex/config.toml` / `hooks.json` | partial |

When you edit any of these global files (this router or a `~/.ai-instructions/` doc), ASK whether to mirror the change to the other tools' files. Never assume.

These local files are the source of truth. They are backed up to the config repo **`ai-agent-orchestration-config`**, cloned alongside your other project repos (NOT under `~`). The repo goes stale until synced. Sync flow: edit the live files → run the repo's own `scripts/capture.ps1` (it copies the live home files into the repo per `sync-manifest.txt`, and refuses any file not in `sync-allowlist.txt`) → commit → push. Files named `*.local.md` carry machine- or project-specific detail: they sync to your own repo but are excluded from any public copy of the instruction set.

## Always-on rules (apply every turn — never skip)
- **Autonomy / permission policy:** Act WITHOUT asking on routine work — reads, worktree edits, file writes, npm/build/test, worktree create/cleanup, `git commit` (on any branch that is NOT main/master), feature-branch push/pull, `git fetch`, `cd`, and MCP calls. ONLY four categories prompt: (1) git ops involving `main` — commit/push/pull/merge/`update-ref` to or from main; (2) history/integration git ops on ANY branch — `merge`, `rebase`, `cherry-pick`; (3) permanent-loss / repo-config git ops — `git stash drop`/`clear` (single-worktree repos only), deleting an unpushed branch, `git tag -d`, `git remote set-url`/`remove`/`rename`; (4) any DB write/edit/delete. Catastrophic ops (delete `.git`, `git worktree remove` outside the cleanup script, ANY mutating `git stash` — bare/push/pop/apply/drop/clear — in a repo with linked worktrees since the stash stack is shared across them, commit secrets/`.env`, workspace-lockfile-corrupting install) are hard-BLOCKED (refused, not prompted). Enforcement lives in `~/.claude/hooks/` PreToolUse scripts + `~/.claude/settings.json`, NOT this prose — editing this bullet changes nothing about what prompts. → `hooks-reference.md`
- **Action Gate:** A question (ends in "?", or "how/what/why/can we/should we…") is NOT permission to act. Answer only; wait for an explicit action verb (do it, build, fix, implement, create).
- **Consent Gate:** For any paid, costly, or hard-to-reverse action (real API spend, bulk/fan-out agent or workflow runs, anything with a $ estimate attached), an `AskUserQuestion` that was interrupted, left unanswered, or followed only by a generic resume/continue message is NOT a yes. Never infer consent from context, from a prior unrelated approval, or from the absence of a "no." Treat it as unanswered and re-ask the specific question in a fresh message before proceeding.
- **Todo discipline:** Any actionable multi-step turn → maintain a live TodoWrite list; exactly one item `in_progress`; mark each item `completed` the instant it's done via its OWN TodoWrite call (never batch) so the full list visibly re-renders with the tick; append new asks rather than dropping current work.
- **Ceremony scales to change size (NEVER safety/verification):** Classify each change first — **Trivial** (1-2 files, no meaningful logic change, no risk area), **Small** (one focused concern, ~≤5 files, no risk area), or **Large/Risky** (feature/multi-concern, OR ANY touch of auth / tenant-isolation / money / migrations / webhooks / public-API / security, regardless of line count). Scale the PAPERWORK to the tier: **design** (Trivial: skip — one-line intent in chat; Small: brief inline plan, no separate spec/plan files; Large: full brainstorm→spec→plan→review), **completion summary** (Trivial: 1-2 lines; Small: terse 5-section; Large: full 5-section), **workboard mid-flight updates** (Trivial/Small: none needed; Large/parallel: full). **NEVER scale down by size:** worktree isolation, commit/push, workboard register+complete, verification (scope by change → `code-quality.md`), or safety rigor (scale by RISK → the plan-review gate). **Risk overrides size; when unsure, go up a tier.** This OVERRIDES the superpowers `brainstorming` HARD-GATE for Trivial/Small work. → `planning.md`
- **Before reading any code to answer a question or investigate a bug:** run `git -C <repo-root> fetch origin` and read files from `origin/main` (via `git show origin/main:<path>`) or from a worktree checked out at `origin/main`. **Never read or grep the main working tree as a proxy for what is deployed** — the main tree is routinely dirty with uncommitted work-in-progress and will produce wrong answers. The authoritative source is `origin/main`.
- **Before starting any new work:** `git fetch` the base (`main`) and start from the latest — never branch, plan, or build off a stale base. → `git-safety.md`
- **After writing a spec or plan file:** post its key points in chat **in plain English** — the goal / what the feature will let the user do, the handful of decisions that matter, and what's still open — so the user can act without opening the document. Same banned-items list as the completion summary: NO table/file/function names, code identifiers, or raw task-list labels (e.g. "`learnedSenderCategory` service, fail-open"). The technical task breakdown stays in the plan file; chat gets the plain-English version.
- **Plans are intent, not transcription:** in any implementation plan, file paths / line numbers / code snippets are illustrative *as-of-writing* — at execution, locate targets by content/symbol and re-verify signatures; never edit by absolute line number or paste a plan's snippet unchecked. Before executing a plan, run the **plan-review gate**: review the plan's OWN code for tenant-isolation / hardcoded-URL / swallowed-error / `ON CONFLICT`-on-partial-index defects (full adversarial reviewer subagent when it touches auth, tenant data, URLs, migrations, money, or webhooks — a mechanical rename/sweep over DB-coupled strings (onConflict targets, RPC params, backfills) counts as touching migrations and always gets the full gate); don't start while a Critical/High plan-finding is open. (This gate applies when a formal plan exists; per the ceremony-tier rule, Trivial/Small **non-risk** changes may skip the separate spec/plan entirely — nothing to review — but any auth/tenant/money/migration/webhook touch is Large-tier and still gets the full plan + gate.) → `planning.md`
- **Think out loud & plan plainly:** Show reasoning. Plans must be understandable to a non-technical stakeholder and must call out file changes, DB/migration changes, and breaking changes.
- **Shell:** Never `cd` into a subdir — use `--prefix`/`--project`/`--dir`/absolute paths. PowerShell syntax on Windows. **Prefer the native `Grep`/`Glob`/`Read` tools over shelling out to `grep`/`rg`/`find`/`cat`/`ls`/`head`/`tail`** for search, file-listing, and reading — they are ~25× faster per call (no shell spin-up, no pre/post-Bash hook tax) and integrate with permissions. Reserve Bash for actual shell work (pipes, running programs, git).
- **Parallelization (decide BEFORE dispatching anything):** Before spawning ANY subagent, run the three-gate test — (1) **Independent?** (a dependency chain like schema→API→UI→tests is NOT — run it inline); (2) **Substantial?** (bigger than an agent's cold-start/context-reload; tiny → inline); (3) **Headroom?** (fan out to at most `maxConcurrentAgents`, default 4). Only genuinely independent + substantial work fans out, and only as a **concurrent batch** (all dispatched in one message). **BANNED: one-at-a-time sequential subagent dispatch** — it pays full overhead for zero parallelism; do it inline instead. The ONE non-parallel dispatch allowed is a single task too big for one context window (isolation, not speed). Optimize for speed; accept the higher token cost of true parallelism. → `parallel-agents.md`
- **Concurrency cap (gate 3 of Parallelization)** — run `py ~/.ai-instructions/tools/headroom.py` for the number to fan out to. It reads `~/.ai-instructions/parallelization.json` (front-end-drivable): `maxConcurrentAgents` (ceiling/fallback, default 4), `headroomMode` (`live` = size to current machine load, more when idle / fewer when busy; `static` = fixed at the ceiling), `enabled`. Live mode is the default (even if the file is absent); it never exceeds `maxConcurrentAgents` and never drops below 1.
- **Code changes happen in a worktree** — never edit code in the main working tree. **DEFAULT: reuse the scratch worktree** (`py ~/.ai-instructions/tools/scratch_worktree.py <type>/<scope>`) for ANY single-concern task — its `node_modules` persists, so zero install/teardown and zero disk bloat. **The scratch is ONE shared slot per repo across ALL agents/sessions** — recycling it `reset --hard`s away whatever another agent left uncommitted, so the script REFUSES a busy scratch (dirty / unpushed / live <30-min heartbeat); never `--force` past that without being sure it's a dead session, and if two quick fixes run at once only one gets scratch — the other gets a fresh worktree. Spin up a FRESH worktree ONLY when the work is genuinely long-running or runs in PARALLEL with other agents (those need isolation). **Every worktree you create MUST end in a recorded state — there is no "just leave it" option.** Either (a) merged + pushed, then removed with `py ~/.ai-instructions/tools/worktree_cleanup.py <path>` (or automatically, by calling `workboard.py complete`), or (b) committed + pushed and its workboard entry set to `waiting` with a reason. Work that is simply abandoned mid-flight is the single largest source of worktree pileup — if you are stopping, say so on the board before you stop. → `worktree-operations.md`
- **Never leave work uncommitted:** commit inside the worktree as soon as a change is coherent, and ALWAYS before any long-running step (investigation, build, test run, dispatching a concurrent batch of subagents (per the Parallelization rule), or answering a question that needs research). Push after each commit. Uncommitted work has no reflog and no remote copy — it is the only genuinely unrecoverable state in git, and a cleanup that mistakes a zero-commit branch for a finished one will destroy it. The session-end autosave to `wip/<branch>` is a crash backstop, NOT permission to leave work sitting uncommitted. → `worktree-operations.md`
- **Tear down what you start** — any process you spin up for a task (dev server, build/`--watch` watcher, background job, temp file) gets stopped/removed when the task ends. Never leave one running "just in case": orphaned dev servers and node processes accumulate exactly like worktrees and silently eat RAM. → `code-quality.md`
- **Propagating changes** (rename/refactor/schema/signature, or moving a data field between JSON `metadata` and a column / renaming an API field) use expand-contract — never one breaking step; for cross-layer data fields, grep every layer (build green ≠ safe — dynamic reads fail silently) and keep dual-writing until zero readers remain on the old location. ANY rename or schema change first reads the standard process (classify → inventory boundaries → shippable phases → live-evidence verification → contract) — a mechanical sweep additionally follows its sweep-hygiene and post-sweep checks. → `renames-and-schema-changes.md`, `worktree-operations.md`
- **Git:** Never push to main/master without explicit approval; always `git fetch` the base immediately before any merge/update-ref/push to it. Every commit subject uses a Conventional Commits type prefix — `feat:` (new feature), `fix:` (bug fix), `perf:` (user-facing performance improvement), `refactor:` (internal restructuring, no behavior change), `chore:`/`docs:`/`test:` as applicable — optionally scoped, e.g. `feat(billing): add overage credit rollover`. Matches the existing branch-naming convention (`feat/<scope>`, `fix/<scope>`, `refactor/<scope>`, `chore/<scope>`). → `git-safety.md`
- **Per-agent commit identity:** in Claude Code sessions, every `git commit` is automatically rewritten with a distinct author (`Developer (Claude agent-<id>)` / `you+agent-<id>@example.com`) plus an `Agent-Session:`/`Agent-Task:` trailer, enforced by a Claude-Code-specific PreToolUse hook (`pretooluse_bash.py`) — that hook does NOT run in Codex sessions, so this identity is not automatically applied here. If asked to commit in a way that's distinguishable from other agents/sessions later, manually set `-c user.name="Developer (Codex <task-label>)" -c user.email="you+codex-<task-label>@example.com"` on the commit and add the same trailer. Rebase preserves commit AUTHOR (only committer changes), so this survives rebase+FF landing onto main. → `hooks-reference.md`
- **Database:** SQL writes require a dedicated standalone confirmation message; the live DB is the source of truth, not migration files. → `supabase-operations.md`
- **Robustness by default:** when choosing between ways to do something, default to the better, more robust, more correct option — even if it means more effort or more code. Do NOT pick the quick/minimal path to save work; only trade robustness away when the user explicitly says to (e.g. "just hack it", "quick fix", "throwaway"). → `code-quality.md`
- **Problem-solving:** brainstorm options → try the likeliest → diagnose failures → undo before retrying. Never stack failed attempts. → `code-quality.md`
- **Diagnose & fix out loud:** Before diagnosing anything, state in chat the steps you'll take to reach a diagnosis, and post each finding in chat as you discover it. Before fixing a bug/issue, write in chat what the bug/issue is and your plan for fixing it; after fixing, state in chat what you fixed and how. → `code-quality.md`
- **Browser verification:** after a UI/runtime change, end with ONE short offer to verify (Playwright / Lighthouse / heap-diff / network). → `code-quality.md`
- **Coordination & memory — the workboard is MANDATORY, never discretionary:** read `PROJECT_SCOPE.md` / `MEMORY.md` / `WORKBOARD.md` at start. Then for EVERY task that creates a worktree or changes code — no exceptions, no "this one is too small to bother": (1) **register BEFORE your first edit** (`py ~/.ai-instructions/tools/workboard.py register …`); (2) **update it whenever your status or scope changes** (`update-status` / `update-path` / `update-files`) — an entry whose timestamp never moves is treated as abandoned bookkeeping after 14 days and STOPS protecting your worktree from cleanup; (3) **run `workboard.py complete` the moment the work is done** — that call is what triggers worktree cleanup, so skipping it is precisely what leaves worktrees behind forever; (4) **if you stop WITHOUT finishing, set status `waiting` with a reason** — walking away silently is the failure mode that produced 120 abandoned worktrees. **`register` + `complete` are mandatory at EVERY ceremony tier** (they protect the worktree from the sweeper and trigger its cleanup); only the mid-flight `update-*` cadence scales by tier (`planning.md`) — none beyond register+complete for Trivial/Small single-agent work, kept current for Large/parallel work. Update `MEMORY.md` whenever you learn something a future session would otherwise have to rediscover. → `project-setup.md`, `multi-agent-coordination.md`
- **Finishing a plan / phase / stage / wave:** EVERY plan, phase, stage, and wave completion gets a plain-English summary in your reply (individual tasks do NOT — too granular; roll them into the wave's recap). **Plan / phase / stage** get the full FIVE sections, in THIS order, with THESE exact headings — (1) **List of What Was Done** (plain-English checklist, every item ✓ — an outcome a non-technical reader can do/see, NOT a copy of your todo list: no commit hashes, file/function names, "Task N" labels, test counts, or build/`tsc` output — those go under Verification); (2) **Summary Of What Was Done** (plain-English paragraph); (3) **Where To Check** (an in-app walkthrough the user can run — nav path + what to click + what they should see, NOT source-file paths; or an explicit "back-end only — here's how to confirm it"); (4) **Verification** (build/typecheck/lint/tests, for code work); (5) **What's Next** (or "Plan complete."). A **wave** gets a LIGHTER recap instead of the five sections: a concise plain-English "what this wave did + what's next" (1-4 bullets, no Where-to-check/Verification scaffolding). **Also scale depth to change size** (ceremony tiers, `planning.md`): a Large phase → full five sections; a Small/localized phase → a *terse* five-section; a **standalone Trivial/Small change that isn't a formal plan/phase → just a 1-2 line plain-English recap**, no five-section format. Never inflate a one-line fix into five sections. Full format + example → `multi-agent-coordination.md`.
- **Relaying subagent/step work:** a finished subagent's (or `subagent-driven-development` / `executing-plans` task's) own report is for YOU the controller + its report file — NEVER surface it to the user. Give the user a PLAIN-ENGLISH rundown of what was accomplished (+ blockers/decisions/follow-ups). BANNED from that rundown (same list as the completion summary): raw diffs, code snippets, line numbers, file/function names, commit SHAs, test-command output, exit codes, and the `Status / Commits / Test summary / Concerns / report-path` status contract — those stay in the report file only. Parallel subagents → ONE consolidated plain-English rundown. → `multi-agent-coordination.md`
- **Asking the user:** phrase every question or decision request in plain English, and give the context needed to answer it — what's being decided and why, the options with their trade-offs, and your recommendation. Never present bare/terse option cards without that context.
